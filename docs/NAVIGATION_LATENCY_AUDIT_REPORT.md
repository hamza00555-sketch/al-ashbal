# تقرير تدقيق بطء التنقل واستجابة الضغطات — الأشبال

**HEAD المُدقَّق:** `b4f6ff2` (فرع `claude/pensive-hypatia-k6qnf3`)
**التاريخ:** 2026-07-03 · **تدقيق فقط — لا إصلاحات في هذه المهمة.**
**يكمل:** `docs/PERFORMANCE_AUDIT_REPORT.md` (الصور P0 أُصلحت في b4f6ff2).

**منهجية القياس:** بناء إنتاجي محلي + Playwright بجلسة معلمة (خادم Supabase
وهمي محلي حُقن فيه **زمن استجابة 120ms لكل طلب** لمحاكاة supabase.co من
Vercel) + خنق CPU ×4 (هاتف متوسط) على 390×844. عدّاد طلبات في الـ mock يسجّل
كل استدعاء Supabase لكل تنقّل — الأرقام أدناه فعلية لا تقديرية.

## 1) الملخص التنفيذي

**البطء حقيقي + مُدرَك معًا، وسببه الأول واحد: سلسلة استدعاءات Auth متسلسلة
ومكررة عند كل تنقّل داخل /teacher، بلا أي feedback بصري أثناء الانتظار.**

القياس الفعلي (120ms RTT، CPU ×4):

| التدفق | حتى ظهور المحتوى | استدعاءات Supabase |
| --- | --- | --- |
| `/` ← «تسجيل الدخول» (بجلسة ← تحويل للوحة) | **1534ms** | **9** |
| `/teacher` ← درج ← `/teacher/join-requests` (أول مرة) | **1305ms** | **18** (منها 16× getUser!) |
| `/teacher/join-requests` ← درج ← `/teacher` | 825ms | 4 |
| `/teacher` ← درج ← `/teacher/invitations` | 730ms | 1 |
| `/` ← `/login` (بلا جلسة) | 510ms | 0 |
| `/` ← `/join/request` (ثابتة) | **152ms** | 0 |

الاستنتاجات الثلاثة:
1. الصفحات الثابتة سريعة فعلًا (152ms) — البنية سليمة؛ المشكلة محصورة في
   المسارات الديناميكية المحمية.
2. **العدد 18** سببه أمران مركّبان: (أ) سلسلة الطبقات المكررة
   proxy→layout→backend (كل طبقة تنادي getUser مستقلة)، و(ب) **عاصفة
   prefetch**: فتح الدرج يجعل Next يعمل prefetch لروابطه العشرة، وكل
   prefetch يمر بالـ proxy الذي ينادي getUser شبكيًا — فتح الدرج وحده يطلق
   ~10 استدعاءات auth خلفية.
3. **صفر loading.tsx في التطبيق كله** — أثناء الـ 700–1500ms المذكورة لا
   يظهر للمستخدم أي شيء: الزر «ميت» حتى يكتمل عمل الخادم. هذا هو الجزء
   المُدرَك من البطء، وهو الأرخص إصلاحًا.

**أهم 5 إصلاحات موصى بها (بالترتيب):** loading.tsx للمقاطع الديناميكية ·
كاش لكل-طلب (React.cache) يوحّد getUser/profiles · تمرير هوية الـ layout
للصفحات بدل إعادة التحقق · جعل الـ proxy يتحقق محليًا من وجود الكوكي فقط
للـ prefetch (أو تعطيل prefetch في الدرج) · مؤشر تقدم/حالة ضغط فورية للأزرار
الملاحية.

## 2) الأساس المقاس

- الجدول أعلاه + من التدقيق السابق: JS خام لكل صفحة ~570KB عام /
  ~820KB مع Supabase (اللوجين والمناطق المحمية)؛ script time ‏140–250ms
  تحت خنق ×4 — الترطيب ليس عنق الزجاجة.
- التنقلات المتكررة أسرع (730–825ms) لأن prefetch السابق دفع الكلفة مقدمًا —
  أي أن كلفة الدرج الخلفية «تشتري» تنقلات لاحقة أسرع، لكنها تحرق حصة auth.
- الصور لم تعد عاملًا (21KB لصفحة الطفل بعد b4f6ff2).

## 3) النتائج حسب الخطورة

### P1 (لا يوجد P0 — لا شيء يمنع الإطلاق، لكن هذه تحدد جودة الإحساس)

**N1 — لا loading.tsx إطلاقًا (إدراك البطء)**
- الدليل: `find src/app -name loading.tsx` = 0؛ كل تنقّل لمسار ديناميكي
  يعرض لا-شيء حتى اكتمال الخادم (0.7–1.5 ثانية مقاسة).
- الإصلاح: `loading.tsx` بسيط (سبينر/سكيلتون بهوية التطبيق) في
  `src/app/teacher/` و`src/app/parent/` و`src/app/login/` — يجعل الاستجابة
  للضغطة **فورية** لأن Next يعرضه لحظة النقر قبل انتهاء الخادم.
- الخطورة: منخفضة جدًا · الأثر: الأعلى على الإحساس · لا ينتظر.

**N2 — سلسلة auth مكررة متسلسلة لكل طلب /teacher**
- الملفات: `src/proxy.ts` (getUser 1) ← `teacher/layout.tsx`
  resolveTeacherAuth (getUser 2) ← `backend/auth.ts` getCurrentUserProfile
  (getUser 3 + profiles 1) ← getCurrentTeacherProfile (getUser 4 + profiles
  2 + teacher_profiles) ← أفعال/صفحات تنادي requireTeacher (getUser 5 +
  profiles 3). كلها متسلسلة ×120ms.
- الإصلاح: `React.cache()` حول «getUser + قراءة profile» داخل الطلب الواحد
  (يوحّد 5 نداءات إلى 1)، وتمرير `teacherId` من الـ layout حيث يمكن بدل
  requireTeacher المكرر في القراءات (تُبقى requireTeacher في الأفعال
  التحويرية — أمنيًا إلزامية). لا مساس بـ RLS.
- الخطورة: متوسطة (كود auth — QA دقيق) · الأثر: −400–600ms لكل تنقّل.

**N3 — الـ proxy ينادي getUser شبكيًا لكل prefetch**
- الدليل: فتح الدرج = 10 روابط = ~10× GET /auth/v1/user في القياس (العدد 18).
- الإصلاح المقترح: في الـ proxy، معاملة طلبات prefetch (ترويسة
  `next-router-prefetch`) بفحص وجود الكوكي فقط دون تحقق شبكي، أو تعطيل
  prefetch لعناصر الدرج (`prefetch={false}`) — الأول أفضل (يحافظ على فائدة
  السرعة اللاحقة). التحقق الكامل يبقى للطلب الحقيقي.
- الخطورة: متوسطة (سطح أمني — يجب ألا يقدَّم محتوى فعلي بلا تحقق؛ prefetch
  الديناميكي لا يقدّم محتوى الصفحة أصلًا) · الأثر: يلغي عاصفة الخلفية
  ويخفف حصة Supabase.

### P2

**N4 — إعادة تحميل كاملة بعد الدخول/الخروج** — `LoginForm` (assign
  /teacher أو /parent) و`TeacherLogoutButton`/`ParentAccountStatus` (assign
  /login): مقصودة لضمان قراءة الكوكيز الجديدة، وتحدث مرة لكل جلسة — كلفتها
  (~إعادة تنفيذ 600–800KB JS) مقبولة. بديل لاحق: router.replace + refresh
  مع التحقق من عدم رجوع سباق الكوكيز القديم. ليست أولوية.

**N5 — عمل demo-seed في layout المعلم عند كل تنقّل** — `getMockUser` +
  `getNotificationsForViewer` + `getPendingTeacherReviews` تُحسب في الخادم
  لكل طلب — رخيصة (ميلي ثوانٍ) لكنها ستزول بالترحيل. لا تُلمس الآن.

**N6 — chunk مكونات مشترك (51KB) عبر الـ barrel** — كما في التدقيق السابق
  (F5). يزيد الترطيب قليلًا على الصفحات العامة. تحسين لاحق.

### P3

**N7 — حالة الضغط البصرية على روابط التنقل** — الأزرار النموذجية لديها
  busy states جيدة (اللوجين/الطلبات/الموافقة تعطّل وتبدّل النص ✅)، لكن
  روابط الدرج/الشريط السفلي لا تُظهر أي حالة «جارٍ الفتح». مع N1 تصبح شبه
  غير ضرورية. `active:` styles إضافة لطيفة رخيصة.

**N8 — CSS/الحركات: سليمة** — لا transition-all (واحدة فقط)، الدرجان
  transform، لا تأخير أنيميشن قبل التنقل، الدرج يغلق فورًا عند الاختيار،
  ولا overlay يعترض النقرات (أُصلح بالـ Portal في 01a2d53). لا عمل هنا.

**N9 — localStorage**: القراءات داخل useSyncExternalStore بتواقيع مخزنة —
  لا قراءة أثناء التنقل نفسه؛ ليست عاملًا في زمن الضغطة. تزول بالترحيل.

## 4) تشخيص مسارًا-بمسار

- **/** ثابتة، فورية. لا عمل.
- **/login**: ديناميكية (فحص جلسة استباقي). بلا جلسة: 510ms، 0 استدعاءات —
  جيدة. بجلسة: تحويل مزدوج (login→teacher) بسلسلة N2 — يتحسن تلقائيًا معها.
  وأضف loading.tsx.
- **/join/request**: ثابتة، 152ms — مثالية. الإرسال server action بحالة
  busy واضحة ✅.
- **/teacher**: أثقل مسار — N1+N2+N3. أول دخول بعد اللوجين = إعادة تحميل
  كاملة (N4 مقبولة) + السلسلة.
- **/teacher/join-requests**: فوق السلسلة، الصفحة تنادي requireTeacher ثم
  تقرأ القائمة (متسلسلة). الموافقة/الرفض: server action يعيد requireTeacher
  + قراءات admin متسلسلة ثم revalidate — يعمل، ويستفيد من N2، وillusion
  التحسين الفوري (optimistic) تحسين لاحق اختياري.
- **/parent**: نفس نمط الـ layout (getUser+profile لكل طلب) لكن سلسلة أقصر؛
  يستفيد من N1+N2.
- **شاشات الطفل**: localStorage صرفة، سريعة بعد إصلاح الصور؛ الشريط السفلي
  روابط عادية سليمة.

مؤشر تقدم أعلى الصفحة أثناء التنقل · optimistic approve/reject · منع

## 7) فرص الخادم

React.cache لكل-طلب حول getUser+profile · دمج قراءة profiles+teacher_profiles
في استعلام واحد (join أو select مزدوج متوازٍ Promise.all) · تمرير الهوية من
الـ layout للصفحات · proxy خفيف لطلبات prefetch · إبقاء requireTeacher
للأفعال التحويرية كما هي (لا تغيير أمني).
