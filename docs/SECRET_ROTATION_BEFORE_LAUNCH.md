# تدوير مفتاح Supabase السري قبل الإطلاق — خطوة إلزامية

**لماذا؟** أثناء الإعداد الأول مرّ مفتاح `sb_secret_...` (service role — يتجاوز
RLS بالكامل) عبر المحادثة. لا دليل على أي تسريب، لكن القاعدة الأمنية بسيطة:
أي مفتاح خدمة لمس قناة غير مخصصة للأسرار **يُدوَّر قبل دخول مستخدمين حقيقيين**.

> ⛔ **قاعدة الإطلاق: لا تضِف عائلات حقيقية قبل إتمام هذا التدوير.**

## الخطوات (5–10 دقائق، على جهازك — لا تلصق المفتاح في أي محادثة)

1. **أنشئ المفتاح الجديد:** Supabase Dashboard ← Project **al-ashbal** ←
   Project Settings ← **API Keys** ← قسم Secret keys ← **Create new secret
   key** (أو Rotate). انسخ قيمة `sb_secret_...` الجديدة.
2. **حدّث Vercel:** Vercel ← مشروع al-ashbal ← Settings ←
   **Environment Variables** ← عدّل `SUPABASE_SERVICE_ROLE_KEY` بالقيمة
   الجديدة (بيئة Production — وأي بيئة أخرى تستخدمها).
3. **حدّث جهازك:** إن كنت تستخدم `.env.local` محليًا، حدّث فيه نفس المتغير.
4. **أعد النشر:** Vercel ← Deployments ← ⋯ على آخر نشرة ← **Redeploy**
   (المتغيرات الجديدة لا تسري إلا بنشرة جديدة).
5. **تحقق أن التطبيق يعمل:** دخول أسماء من /teacher/login ← فتح
   «طلبات الانضمام» ← وجرّب موافقة/رفض طلبًا تجريبيًا واحدًا (الموافقة تمر
   عبر مفتاح الخدمة، فنجاحها = المفتاح الجديد سليم).
6. **ألغِ المفتاح القديم:** ارجع إلى API Keys واحذف/عطّل مفتاح
   `sb_secret` القديم (Revoke). *لا تحذفه قبل نجاح الخطوة 5.*

## ملاحظات

- مفتاح `sb_publishable_...` (العام) **لا يحتاج تدويرًا** — هو مصمم ليكون
  عامًا ومقيّدًا بـ RLS.
- إن فشل شيء بعد التدوير: الأعراض المتوقعة هي فشل «الموافقة على الطلبات»
  و«إرسال طلب انضمام» فقط (هما مسارا مفتاح الخدمة) — راجع قيمة المتغير في
  Vercel ثم أعد النشر.
- لا حاجة لتغيير أي كود — القيمة تُقرأ من المتغيرات فقط.

## قائمة الإطلاق المختصرة

- [ ] مفتاح sb_secret جديد أُنشئ.
- [ ] Vercel محدَّث + أعيد النشر.
- [ ] .env.local المحلي محدَّث (إن وُجد).
- [ ] دخول أسماء + موافقة تجريبية نجحا بعد التدوير.
- [ ] المفتاح القديم أُلغي.
- [ ] عندها فقط: ابدأ بإضافة العائلات الحقيقية.
