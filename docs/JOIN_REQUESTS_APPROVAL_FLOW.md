# طلبات الانضمام والموافقة — Join Requests & Approval Flow

تدفّق انضمام مضبوط: المستخدم الجديد **يطلب** الوصول، ومعلمة معتمدة **توافق** قبل
تفعيل أي صلاحية. لا حاجة بعد الآن لإنشاء المستخدمين يدويًا من لوحة Supabase.

---

## ما الذي أُضيف

| العنصر | المكان |
| --- | --- |
| جدول `join_requests` + سياسات RLS + دالة `is_app_teacher()` | `supabase/migrations/011_join_requests.sql` (مطبّقة على المشروع الحي) |
| صفحة الطلب العامة | `/join/request` — `src/app/join/request/` |
| صفحة المراجعة للمعلم | `/teacher/join-requests` — في قائمة المعلم الجانبية «طلبات الانضمام» |
| منطق الخادم | `src/lib/backend/joinRequests.ts` + server actions |
| شاشات «قيد المراجعة» / «مرفوض» | بوابة `/teacher` (layout + TeacherAccessDenied) |

## التدفّق

1. **الطلب** (`/join/request`، عام): الاسم + البريد + كلمة مرور + نوع الطلب
   (معلم / ولي أمر) + ملاحظة اختيارية. عند الإرسال يُنشأ من الخادم:
   - مستخدم Supabase Auth (بريد مؤكَّد) **بلا صف profiles** — أي بلا أي صلاحية.
   - صف `join_requests` بحالة `pending`.
   طلب معلّق سابق لنفس البريد → «لديك طلب سابق قيد المراجعة.» (فهرس فريد جزئي
   يمنع التكرار حتى في السباقات). بريد لعضو مفعَّل → «مسجّل بالفعل».
2. **المراجعة** (`/teacher/join-requests`، للمعلمين المعتمدين فقط):
   - **موافقة معلم**: profiles بدور `teacher` + `teacher_profiles` + ربط
     بالحلقة الافتراضية (أقدم حلقة نشطة) + تحديث الطلب (`approved`،
     `reviewed_by`، `reviewed_at`).
   - **موافقة ولي أمر**: profiles بدور `parent` + `parent_profiles` + تحديث
     الطلب. **لا يُنشأ أطفال ولا روابط أطفال في هذه المرحلة.**
   - **رفض**: الحالة `rejected` + بيانات المراجعة. لا صلاحية.
3. **سلوك الدخول بعد الطلب** (على `/teacher`):
   - معلّق: «طلبك قيد المراجعة. ستتمكن من الدخول بعد الموافقة.»
   - مرفوض: «تم رفض طلبك. تواصل مع المسؤول إذا كنت تعتقد أن هناك خطأ.»
   - موافَق عليه كمعلم: تفتح لوحة المعلم.
   - ولي أمر (بأي حالة): لا يدخل لوحة المعلم («هذا الحساب ليس حساب معلم»).
     واجهة ولي الأمر الحقيقية تأتي في مرحلة لاحقة — الموافقة تجهّز الحساب فقط.

## الأمان (RLS + حدود الخادم)

- `join_requests`: RLS مفعّل. anon **صفر** وصول (لا تعداد بريدات).
  authenticated يقرأ **طلبه هو فقط** (`auth_user_id = auth.uid()`)، والمعلم
  المعتمد يقرأ الكل عبر `is_app_teacher()` (SECURITY DEFINER + search_path
  مثبّت + بلا EXECUTE لـ anon — نفس نمط 009).
- **لا سياسات كتابة للعملاء إطلاقًا** على الجدول: الإنشاء والمراجعة يمران حصرًا
  عبر الخادم (service role) بعد تحقّقه الخاص — الموافقة/الرفض خلف
  `requireTeacher()` في server actions. مفتاح الخدمة لا يصل المتصفح أبدًا.
- إنشاء مستخدم Auth عند الطلب لا يمنح شيئًا: بلا صف profiles، وكل سياسات
  التطبيق تشترط دورًا حقيقيًا.

## لماذا الأطفال ليسوا مستخدمي Auth في هذه المرحلة

الأطفال يبقون **child profiles** (جدول `children`) بلا حسابات Auth: أصغر سطح
أمان وأبسط تجربة (لا بريد/كلمة مرور لطفل). ربطهم يأتي لاحقًا عبر دعوات العائلة
وأكواد وصول الطفل (`child_device_grants` — مسار محكوم من الخادم بتصميم H1).

## ما زال localStorage (لم يُرحَّل عمدًا)

الدعوات التجريبية (`/join?code=...` تعمل كما هي — `/join/request` مسار منفصل)،
الأطفال/التسليمات/التسجيلات/النقاط/التقدم، وتجربتا الطفل وولي الأمر كاملتان.

## حدود معروفة

- لا إشعار بريدي للمعلمة عند وصول طلب، ولا للطالب عند الموافقة (يدوي حاليًا).
- «سبب الرفض» عمود موجود في الجدول دون واجهة إدخال بعد.
- ولي الأمر الموافَق عليه لا يملك لوحة بعد — حسابه جاهز للمرحلة القادمة.
- صفحة `/join/request` عامة: يمكن إرسال طلبات مزعجة — المراجعة اليدوية هي
  الحاجز (مقبول للتجربة المغلقة).

## التوصية للمرحلة التالية

ترحيل دعوات العائلة/الطلاب إلى Supabase وربطها بحسابات أولياء الأمور المعتمدين
(parent_child_links + children)، ثم واجهة ولي الأمر الحقيقية، ثم التسليمات
والتسجيلات (bucket خاص + مسارات موقّعة).
